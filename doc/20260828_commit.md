# 변경사항 정리 (리본 "삽입" 탭 — 자주 쓰는 블록 즐겨찾기)

커밋 전 정리용 문서. 지난 커밋(`664fa89`, 2026-08-27, "보이는ARS화면 SCRIPT 창에서
표출가능하도록 변경") 이후 진행된 작업은 아래 열 덩어리입니다.

1. 리본 "삽입" 탭 — 자주 쓰는 블록(즐겨찾기) 수동 등록
2. 캔버스 블록 아이콘 — glossy 재도색 + 아이콘 배지 on/off
3. 버그 수정 — "프로젝트 열기"로 불러온 블록이 무색으로 보이던 문제
4. 파일 로드 시 겹친 블록 자동 해소 (가벼운 버전)
5. 나머지 블록 아이콘 37종 glossy 재도색
6. "정렬" 탭 — 그래프 구조 기반 자동 정렬 (위→아래 / 왼쪽→오른쪽)
7. `CustomBlock` 이벤트 행 접기/펼치기 (이벤트 많은 블록의 세로 길이 문제)
8. 버그 수정 — 겹친 링크 배지가 항상 좌표 (0,0) 근처에 잘못 표시되던 문제
9. `CustomBlock`의 "+" 버튼 — 네이티브 목록 대신 `LinkEventPicker` 재사용
10. Circle/Diamond 노드도 Custom 모드에서 `CustomBlock`으로 — 링크 겹침을
    구조적으로 제거

## 1. 리본 "삽입" 탭 — 자주 쓰는 블록(즐겨찾기) 수동 등록

66종 노드가 카테고리 플라이아웃 뒤에 숨어 있어서, 자주 쓰는 블록도 매번 카테고리를
열고 찾아야 하는 게 번거롭다는 요청. 처음엔 "사용 빈도를 자동으로 추적해서
보여주는 것"으로 이해하고 그 방향으로 검토를 시작했으나, 사용자가 **자동 집계가
아니라 사용자가 "+"로 직접 등록하고 "×"로 직접 빼는 수동 핀 고정**이 의도라고
정정 — 설계를 그에 맞게 다시 진행했다.

- 즐겨찾기 줄은 카테고리 플라이아웃처럼 클릭해야 열리는 게 아니라 "삽입" 탭을 열면
  **항상 펼쳐진 채로** 보인다 — 또 다른 플라이아웃 뒤에 숨기면 "찾으러 들어갈 필요
  없게" 하려는 애초 목적에 어긋나기 때문. "+"(추가)와 각 타일의 "×"(제거)만
  클릭으로 여닫히는 부분.
- 최대 8개(`MAX_FAVORITES`). 꽉 찬 상태에서 "+"로 추가를 시도하면 토스트 알림
  ("즐겨찾기는 최대 8개까지예요. 먼저 하나를 빼주세요.")으로 안내하고 추가는
  막는다.
- 시나리오 `.xml`에는 안 들어가는 개인 UI 습관이라 `localStorage`
  (`ribbon.insertFavorites` 키)에 저장 — 스크립트 모달 크기 기억과 같은 저장소/이유.

**추가된 파일**
- `src/lib/insertFavorites.js` — `getFavorites`/`addFavorite`/`removeFavorite`
  (localStorage 기반, try/catch로 프라이빗 브라우징 등 방어), `MAX_FAVORITES = 8`.

**수정된 파일**
- `src/components/RibbonMenu.jsx` — `FavoritesRow`(항상 펼쳐진 즐겨찾기 줄 + "+"
  토글 + 빈 상태 안내 문구), `AddFavoriteFlyout`(카테고리 구분 없이 전체 66종을
  한 검색창에서 찾는 추가용 팝오버 — 이미 등록된 항목은 "✓" 표시 후 비활성화),
  리본 전역 토스트 state(`toast`/`showToast`, 2.5초 후 자동 소멸, 특정 플라이아웃
  안에 넣으면 그 플라이아웃이 닫힐 때 같이 사라지므로 리본 최상단에서 관리).
  `RibbonButton`에 `style` prop 추가(그룹 색상 CSS 변수를 통과시키기 위함).
- `public/css/ribbon-menu.css` — `.ribbon-insert-tab`/`.ribbon-favorites-row`/
  `.ribbon-favorites-empty`/`.ribbon-favorite-tile`/`.ribbon-favorite-remove`
  (호버 시에만 보이는 "×")/`.ribbon-favorite-add-wrap`/`.ribbon-favorite-add`
  (점선 테두리 "+")/`.ribbon-toast`(화면 하단 중앙 고정) 신규.

**검증 (Playwright)**: 빈 상태 안내 문구 표시 → "+" 클릭 시 66종 전체 검색
플라이아웃이 열리고 항목 클릭마다 즐겨찾기 줄에 타일로 추가됨 → 이미 등록된
항목은 플라이아웃에서 "✓" + 비활성 표시 → 8개를 채운 뒤 9번째 추가 시도 시 타일
개수는 8개로 유지되고 토스트가 정확한 문구로 뜸 → 2.5초 후 토스트 자동 소멸 →
타일에 마우스를 올리면 "×"가 나타나고 클릭하면 그 타일만 제거(개수 7로 감소,
다른 타일엔 영향 없음) → 타일 본문 클릭 시 카테고리 플라이아웃의 항목과 동일하게
삽입 모드로 전환(`is-active` 부여) → 페이지를 새로고침해도 즐겨찾기 7개가
`localStorage`에서 그대로 복원됨. 콘솔 에러 없음.

**버그 발견 및 수정 (1) — 추가 플라이아웃이 화면 밖으로 렌더링**

검증 도중 추가용 플라이아웃(`AddFavoriteFlyout`)이 화면 밖(음수 x좌표)으로
렌더링되는 문제를 발견 — `.ribbon-favorite-add-flyout`에 준 `right: 0` 오버라이드가
"+"가 앵커된 wrap의 오른쪽 끝에 플라이아웃의 오른쪽 끝을 맞추는 것이었는데, "+"가
화면 왼쪽/가운데 즈음에 있을 때가 많아 플라이아웃(최대 480px)이 그만큼 왼쪽으로
밀려나 화면 밖으로 나가버렸다. 오버라이드를 제거해 `.ribbon-insert-flyout`의
기본값(`left: 0`, "+"에서 오른쪽으로 펼침, 카테고리 플라이아웃과 동일한 방향)을
그대로 물려받도록 수정 — 재검증 시 바운딩 박스 x좌표가 전부 양수로 화면 안에
들어옴을 확인.

**버그 발견 및 수정 (2) — 캔버스 클릭 시 추가 플라이아웃이 안 닫힘**

"+" 추가 플라이아웃이 열린 채로 캔버스의 anchor(블록 가장자리 연결점)를 클릭하면
안 닫히는 문제가 있었음 — `diagram-library.js`의 `Anchor._mousedown` 등이 그
이벤트에 `e.stopPropagation()`을 걸어서(다른 mousedown 핸들러들은 이 호출이
없음), 버블 단계로 등록된 바깥클릭 감지 리스너까지 이벤트가 아예 도달하지 못했음.
`FavoritesRow`의 바깥클릭 리스너를 캡처 단계로 변경(`document.addEventListener('mousedown',
handler, true)`) — 캡처는 이벤트가 대상까지 내려가는 길에 먼저 실행되므로 그
`stopPropagation()`보다 앞서 걸림. Playwright로 캔버스에 블록을 하나 놓고 (1) 블록
몸통 클릭 (2) 블록 가장자리(anchor 근처) 클릭 둘 다 플라이아웃이 정상적으로
닫히는 것을 확인.

**버그 발견 및 수정 (3) — 즐겨찾기 타일이 전부 파란색으로만 보임**

즐겨찾기 타일과 추가 플라이아웃의 항목이 전부 기본 파란색으로만 보이던 문제 —
카테고리 버튼/플라이아웃은 `.ribbon-insert-category`가 `groupColorStyle(groupName)`
(`--group-color`/`--group-color-bg` CSS 변수)을 얹어서 자식 `.ribbon-button-icon-placeholder`가
그 그룹 색을 물려받는데, 즐겨찾기 쪽엔 이 변수가 전혀 안 꽂혀 있어 CSS 기본값
(파란색)만 계속 쓰이고 있었음. `RibbonButton`에 `style` prop을 추가해 통과시키고,
`FavoritesRow`의 각 `.ribbon-favorite-tile`과 `AddFavoriteFlyout`의 각 항목에
`style={groupColorStyle(def.group)}`을 꽂아 노드 자신의 그룹(시나리오/컨트롤/음성/
서비스) 색을 쓰도록 수정. Playwright로 각기 다른 그룹의 노드 4개를 즐겨찾기에
추가해 컴퓨티드 배경/아이콘 색이 그룹별로 다르게(파랑/주황/청록/주황) 나오는 것을
확인.

## 2. 캔버스 블록 아이콘 — glossy 재도색 + 아이콘 배지 on/off

블록 아이콘이 66종 다 똑같은 4색 파스텔 배경 위에 검은 아이콘이라 단조롭다는
지적에서 시작 — 여러 단계 검토(아이콘 색만 흰색으로 바꾸는 안, DB 블록을 예로
직접 그려본 입체 일러스트 아이콘 등) 끝에, 10종을 골라 그라디언트+하이라이트+
드롭섀도우로 입체감을 준 "glossy" 스타일로 다시 그리고, 배지 자체를 껐다 켰다
할 수 있는 토글을 추가하기로 확정.

**아이콘 10종 재도색** — `public/icons/`의 실제 파일을 그 자리에서 교체(파일명
동일, 코드 변경 없이 `<img src="icons/...">`가 자동으로 새 그림을 불러옴):
`start`/`gotopage`(시나리오, 파랑), `if`/`transfer`/`pause`(컨트롤, 주황),
`prompt`/`asr`/`getttsstream`(음성, 청록), `servicestart`/`dbexecute`(서비스,
보라 — DB만 처음부터 새로 그린 실린더 일러스트, 나머지 9개는 기존 flat 아이콘의
원본 path는 그대로 두고 레시피만 얹음).

**레시피(9개 공용)**: 같은 path를 두 번 그린다 — ① 그룹 원색→어두운 톤 그라디언트로
채우고 얇은 진한 윤곽선을 두른 몸통 레이어, ② 그 위에 옅은 흰색 sheen 그라디언트
오버레이. 여기에 드롭섀도우 한 겹. 지오메트리를 새로 그릴 필요 없이 색 레이어만
더하는 방식이라 10개를 빠르게 만들 수 있었다.

**한 번 수정함 — 배지 없이 보면 아이콘이 흐려 보이던 문제**: 처음 버전은 그라디언트
밝은 쪽 끝을 흰색에 가까운 톤으로 잡았는데, 배지(색 있는 사각 배경)를 끄고 보니
그 밝은 부분이 블록 자체의 옅은 파스텔 배경과 명도 차이가 거의 없어 실루엣이
흐려졌다(전화기·사운드웨이브처럼 선이 얇은 아이콘일수록 심함). ① 그라디언트 밝은
끝을 흰색 대신 그룹 원색으로 낮추고 ② 흰색 sheen을 옅고 좁게 줄이고 ③ 실루엣
가장자리에 얇은 진한 윤곽선을 추가해 배경이 뭐든 형태가 또렷하게 남도록 재조정 —
배지 on/off 두 상태 모두에 이 통일된 버전을 그대로 씀.

**아이콘 배지 on/off 토글**: 실사용 블록 도형(Rectangle2Block/CircleBlock2/
DiamondBlock2/CustomBlock)이 전부 `classPrefix='hd-block2'`를 공유해서 아이콘
배지 div가 도형 종류와 무관하게 전부 `.hd-block2-iconarea`라는 같은 클래스로
잡힌다(diagram-library.js 확인) — 그래서 `diagram-library.js`를 전혀 안 건드리고
CSS 클래스 하나(`.badges-off .hd-block2-iconarea { background-color: transparent
!important; }`)로 전체 배지를 한 번에 켜고 끌 수 있었다. 리본 "보기" 탭(확대/축소
옆)에 "표시" 그룹을 새로 만들어 "아이콘 배지" 토글 버튼 추가. 시나리오 `.xml`과
무관한 개인 UI 취향이라 `localStorage`(`diagram.showIconBadges` 키)에 저장 —
즐겨찾기/스크립트 모달 크기와 같은 패턴.

**추가된 파일**
- `src/lib/iconBadgePref.js` — `getIconBadgesVisible`/`setIconBadgesVisible`
  (localStorage 기반, 기본값 true = 기존처럼 배지 표시).
- `public/css/block-badge.css` — `.badges-off .hd-block2-iconarea` 오버라이드
  한 줄.

**수정된 파일**
- `public/icons/{start,gotopage,if,transfer,pause,prompt,asr,getttsstream,
  servicestart,dbexecute}.svg` — glossy 레시피로 전면 재도색.
- `src/components/DiagramCanvas.jsx` — `useStylesheet('/css/block-badge.css')`
  추가, 캔버스 생성 시 저장된 배지 표시 여부를 `diagram.svg`에
  `badges-off` 클래스로 적용, `useImperativeHandle`에 `setIconBadgesVisible(visible)`
  메서드 추가(클래스 토글 + localStorage 저장을 한 번에 처리).
- `src/components/RibbonMenu.jsx` — "보기" 탭에 "표시" 그룹 + "아이콘 배지"
  토글 버튼(`showIconBadges` state, 클릭 시 `call('setIconBadgesVisible', ...)`).

**검증 (Playwright)**: 6개 그룹·타입에 걸쳐 블록을 놓고 기본(배지 켜짐) 상태
스크린샷 확인 → "보기" 탭 토글 클릭 시 버튼의 `is-active`가 꺼지고 `diagram.svg`에
`badges-off` 클래스가 실제로 붙는 것 확인 → 배지가 꺼진 상태에서도 6개 아이콘
전부(전화기·사운드웨이브 포함) 윤곽선 덕분에 또렷하게 보임 → 새로고침 후에도
`localStorage`에서 꺼짐 상태가 그대로 복원됨. 콘솔 에러 없음.

**특이점**
- `diagram-library.js`는 이번에도 전혀 건드리지 않음 — 아이콘은 정적 자산 교체,
  배지 토글은 CSS 클래스 하나로 해결.
- 배지 배경색 자체(`iconArea.style.backgroundColor`)나 `bg-color`/`icon-color`
  직렬화 로직은 손대지 않았음 — 화면 표시만 CSS로 가리는 방식이라 저장된 `.xml`
  파일의 내용이나 undo/redo에는 전혀 영향 없음.

## 3. 버그 수정 — "프로젝트 열기"로 불러온 블록이 무색으로 보이던 문제

사용자가 실제 프로젝트(.prj + .xml)를 "프로젝트 열기"로 불러왔을 때 블록에 색이
하나도 안 입혀져 있는 걸 발견 — 원인 조사 결과, 레거시 ScenarioDesigner XML을
변환하는 `designerXml.js`가 `group` 개념 자체를 몰라서 변환된 `<block>`에
`bg-color`/`icon-color` 속성을 전혀 안 남기고 있었다. `Block.deserialize()`
(diagram-library.js)는 이 두 속성이 없으면 `null`을 그대로 `shapeElement.style.fill`
/ `iconArea.style.backgroundColor`에 대입하는데, `null`은 사실상 "색 없음"이라
블록이 무색으로 보였던 것.

리본에서 직접 블록 하나를 삽입할 때는 `applyGroupColorToNewestBlock()`이 방금
만든 블록에 그룹 색을 입혀주지만, 파일을 통째로 불러오는 경로(`Diagram.deserialize()`)는
이 함수를 안 거치기 때문에 지금까지 이 문제가 안 잡혔다.

**수정**: `DiagramCanvas.jsx`에 `backfillMissingBlockColors(diagram, meta)`를
추가 — 캔버스 생성 직후 모든 블록을 훑어서, `shapeElement.style.fill`이 비어있는

있으므로 건드리지 않는다 — 오직 "색 정보가 아예 없는" 경우에만 채워 넣는다.
`diagram-library.js`/`designerXml.js`는 손대지 않았다.

**검증 (Playwright)**: 실제 `123.prj`+`123.xml`(140개 블록)을 "프로젝트 열기"로
불러온 뒤, 블록 15개를 샘플링해 `fill` 값을 확인 — 전부 그룹별 실제 tint 색상

블록 전부 그룹 색 + 아이콘이 정상적으로 보이는 것 확인.

**참고**: 작업 중 `src/lib/diagram-library.js`의 `.hd-block2` 스타일(테두리 색
`#888888`→`#b9b9b9`, 드롭섀도우를 `2px 2px 8px rgba(0,0,0,0.5)`→`1px 1px 5px

**수정된 파일**

## 4. 파일 로드 시 겹친 블록 자동 해소 (가벼운 버전)

"파일을 불러왔을 때 블록 간격을 균등하게 분배해서 가시성 좋게 보여줄 수 있는지"
검토 요청 — 그래프 구조를 이해하고 통째로 다시 배치하는 무거운 자동 정렬(`dagre` 같은
계층형 레이아웃 라이브러리 필요, 방향(top-down/left-right) 선택까지 포함해서
검토는 마쳤지만 별도 의존성과 UX 결정이 필요)과, **지금 배치는 그대로 두고 실제로
겹치거나 너무 붙어있는 것만 살살 벌리는 가벼운 버전** 두 가지를 검토한 뒤, 사용자가
후자로 먼저 진행하기로 결정.

**알고리즘**: 겹친 두 블록/메모의 바운딩 박스를 찾아서, 겹침이 더 작은 축(가로 또는
세로) 방향으로 절반씩 밀어 떼어놓는 걸 여러 번 반복 — 타일/태그 클라우드에서 흔히
쓰는 단순 겹침 해소 기법이라 그래프 레이아웃 라이브러리가 필요 없다. 최소 여유
간격(`MIN_GAP=12px`)까지 포함해서 판정하므로 딱 붙어있는 것도 살짝 벌어진다. 실제로
안 겹치는 블록은 전혀 안 건드리므로 "대충 유지" 요구사항을 만족한다.

**그룹 멤버는 건드리지 않음**: `reconcileGroupBounds`(blockGrouping.js)가 그룹
멤버를 이미 정해진 고정 박스 안으로 다시 밀어넣기만 하고 박스 자체는 안 넓혀주기
때문에, 자동 겹침 해소가 멤버를 옮기면 이 로직과 서로 밀고 당기며 싸우게 된다 —
`findGroupRecordForMember()`로 그룹에 속한 블록은 이번 패스에서 아예 건너뛴다(알려진
제한, 그룹 안에서 겹친 경우는 다음 단계에서 다룰 대상).

**추가된 파일**
- `src/lib/blockSpacing.js` — `relaxOverlappingBlocks(diagram)`.

**수정된 파일**
- `src/components/DiagramCanvas.jsx` — 그룹 레지스트리가 채워진 뒤
  (`rehydrateGroupsAfterDeserialize` 다음, `syncLinkOverlapBadges`보다 먼저)
  `relaxOverlappingBlocks(diagram)` 호출.

**검증 (Playwright, 실제 `123.prj`+`123.xml` 140개 블록)**: 기능을 잠깐 꺼서
측정한 원본 데이터의 실제 겹침 쌍 16개(엄격한 바운딩 박스 기준) → 기능을 켜고
다시 로드하니 0개로 전부 해소. 로드+겹침해소에 걸린 시간 약 3초(파일 읽기 UI
자체의 시간이 대부분, 계산 자체는 140개 블록 기준으로 매우 빠름). 콘솔 에러 없음.
전체 화면 스크린샷으로도 원래 배치가 크게 안 흐트러진 채(축소 100%→26% 전후
비교) 유지되는 것 확인 — "대충 유지 + 겹친 것만 벌리기" 의도대로 동작.

**특이점**
- `diagram-library.js`는 이번에도 전혀 건드리지 않음 — 기존에 이미 있던
  `block.setPosition(x, y, true)`(정렬 탭의 가로/세로 균등 분포 기능이 쓰는 것과
  동일한 API)만 사용, 앵커/링크 재계산은 라이브러리가 알아서 처리.
- 다음 단계로 검토했던 "구조 자체를 다시 짜는 자동 정렬"(top-down/left-right
  방향 선택 포함)은 이번엔 진행하지 않음 — 이 가벼운 버전이 부족하다고 판단되면
  그때 `dagre` 추가를 다시 검토하기로 함.

## 6. "정렬" 탭 — 그래프 구조 기반 자동 정렬 (위→아래 / 왼쪽→오른쪽)

지난 검토(4번, "가벼운 버전")에 이어 무거운 쪽 — 그래프 구조(블록+방향성 있는
링크)를 이해해서 통째로 다시 배치하는 자동 정렬을 진행. 검토 때 얘기한 대로
방향(top-down/left-right) 선택도 같이 넣었다.

**의존성 추가**: `@dagrejs/dagre`(원조 `dagre`는 사실상 유지보수 중단, 이쪽이
DagreJS 조직에서 관리하는 후속 버전) — 계층형(Sugiyama) 그래프 레이아웃 라이브러리.
API는 클래식 dagre와 동일(`dagre.graphlib.Graph` + `dagre.layout(g)`).

**추가된 파일**
- `src/lib/autoLayout.js` — `runAutoLayout(diagram, direction)`. 그룹 멤버가
  아닌 블록만 모아 dagre 그래프의 노드로(`width`/`height`는 블록 실제 크기),
  두 끝이 전부 그 안에 있는 링크만 엣지로 등록 → `dagre.layout(g, { rankdir,
  nodesep: 40, ranksep: 70 })` 실행 → 결과 좌표(dagre는 노드 "중심" 기준으로
  돌려줌 — 블록의 좌상단 기준 `x`/`y`로 변환)로 각 블록을 `setPosition(rx, ry,
  true)`.

**Undo/Redo는 새 액션 타입을 안 만들고 기존 것을 재사용**: `ActionManager.append()`가
화이트리스트 방식이라(`diagram-library.js`) 새 상수를 쓰려면 라이브러리에 분기를
추가해야 하는데, "블록별로 다른 상대 이동량 `{block, rx, ry}` 목록"이라는 모양이
"정렬" 탭의 가로/세로 균등 분포가 이미 쓰는 `ActionManager.COMPONENTS_ALIGNED`와
완전히 같아서 그대로 재사용 — `diagram-library.js`는 이번에도 전혀 안 건드림.

**그룹 멤버는 이번에도 건드리지 않음**: 4번 항목과 같은 이유(`reconcileGroupBounds`가
멤버를 고정 박스 안으로 다시 밀어넣기만 함) — 그룹 전체를 하나의 노드로 취급해서
통째로 옮기는 처리는 다음 단계 과제로 남김. 몇 개가 제외됐는지는 토스트로 안내.

**UI**: "정렬" 탭에 기존 균등 분포 버튼들과 별개로 "자동 정렬 (전체)" 그룹 신설,
"위→아래로"/"왼쪽→오른쪽으로" 버튼 2개. 파일을 열 때마다 자동 실행하는 게 아니라
사용자가 원할 때 누르는 방식으로 결정(검토 때 얘기한 대로 — 원본 배치를 매번
덮어쓰면 저장 시 되돌릴 수 없어짐). 실행 결과("N개 블록을 재배치했어요, 그룹에
속한 M개는 그대로 둠")를 리본 토스트로 안내.

**버그 발견 및 수정 (1) — 재배치 후 빨간 점선 가이드선이 화면에 남음**: 검증 중
`block.setPosition()`이 내부적으로 `diagram.drawHelperLine()`(드래그 중 다른
블록과 좌표가 맞는지 보여주는 빨간 점선 스냅 가이드)을 매번 다시 그린다는 걸
발견 — 여러 블록을 반복 이동하는 루프 끝에 마지막으로 옮긴 블록의 가이드선이
지워지지 않고 남아있었다. 기존 "정렬" 탭의 `align()`이 루프 끝에
`this.removeHelperLine()`을 호출해 이미 처리하고 있던 것과 똑같이,
`autoLayout.js`와 (지난번에 만든) `blockSpacing.js` 양쪽 다 루프 끝에
`diagram.removeHelperLine()`을 추가해서 해결.

**버그 발견 및 수정 (2) — 왼쪽→오른쪽 정렬인데 링크가 위/아래 anchor로 붙음**:
사용자 피드백으로 발견 — `block.setPosition()`은 블록 위치만 바꿀 뿐, 그
블록에 붙은 링크가 어느 anchor(L/T/R/B)에 연결돼 있는지는 전혀 안 바꾼다.
그래서 왼쪽→오른쪽으로 재배치해도 링크는 재배치 전(원래는 위아래로 뒤섞여
있던 배치에 맞춰 정해진) anchor에 그대로 붙어있어서, 블록은 옆으로 나란히
섰는데 링크는 위/아래 anchor로 뒤로 돌아나가는 모양이 됐다. 원인 확인 결과
`Link`에는 anchor를 바꿔 끼우는 공개 메서드가 아예 없음(사용자가 링크 끝을
직접 드래그해서 재연결할 때조차 `diagram-library.js`는 기존 링크를
`remove()`하고 완전히 새 `Link`를 만드는 방식). 새로 만들지 않고
`anchorFrom`/`anchorTo`/`posOrigin`/`posDest`를 직접 갈아끼우는 방식으로
수정 — `Anchor` 객체 자체는 "어떤 링크가 자길 쓰는지" 추적하지 않아서
(diagram-library.js 확인) 필드 재할당만으로 충분하고, 링크 id도 그대로라
다른 곳의 id 참조도 안 깨진다. 방향별 anchor 쌍은 TB→(B에서 나가 T로 들어감),
LR→(R에서 나가 L로 들어감). 기존 곡선 휨 정도(`moveX`/`moveY`)는 이전 anchor
기준으로 튜닝된 값이라 새 anchor에는 안 맞을 수 있어 0으로 리셋.
  - **알려진 제한**: 이 anchor 재연결은 실행 취소 대상이 아니다 — 링크 하나당
    별도 undo 스텝이 되는 기존 `LINK_CONNECT_CHANGED`를 재사용하면 "한 번
    클릭 = 한 번 실행 취소"가 깨지고, 실행 취소 스택 한도를 넘기면 정작 블록
    위치를 되돌리는 항목이 먼저 밀려날 위험이 있어 일부러 안 붙였다. 실행
    취소를 누르면 블록 위치는 정확히 복원되지만, 링크는 재배치 당시 붙었던
    anchor에 남아있는다(잘못 이어지거나 깨지진 않음 — 그냥 재배치 전 모습으로
    완전히 안 돌아갈 뿐).

**검증 (Playwright, 실제 `123.prj`+`123.xml` 140개 블록, 자기참조 제외 299개 링크)**:
- "위→아래로" 클릭 → 140개 전부 실제로 좌표 변경, 토스트에 정확한 개수 표시.
- "실행 취소" 클릭 → 140개 전부 원래 좌표로 정확히 복원(부동소수점 오차 없이).
- 전체 화면을 축소해서 확인 — 위→아래/왼쪽→오른쪽 두 방향 다 실제로 레이어별로
  깔끔하게 줄지어 배치됨(원래의 뒤섞인 배치와 뚜렷이 다름).
- 가이드선 버그 재현 스크린샷으로 확인 후, 수정 뒤 재확인 — 깨끗함.
- anchor 버그 수정 직후(당시) 검증: "왼쪽→오른쪽으로" 실행 시 링크 299개 전부
  `anchorFrom.position==='R' && anchorTo.position==='L'`로 나왔었음 — **그런데
  이 검증 자체가 놓친 케이스가 있었다는 게 나중에 실사용 중 드러남 (아래
  "버그 발견 및 수정 (3)" 참고)**.
- 콘솔 에러 없음(단, 이후 실사용 중 다른 크래시 발견 — 아래 참고).

**버그 발견 및 수정 (3) — 사용자가 실사용 중 발견: 왼쪽→오른쪽 정렬 후 블록을
움직이면 크래시**

사용자가 실제로 "왼쪽→오른쪽으로" 정렬을 쓰다가 아래 두 에러를 만남:
```
Uncaught TypeError: Cannot read properties of undefined (reading 'x')
    at Link.adjustPoints (diagram-library.js:5404:38)
    ... at CircleBlock2.setPosition ...
Uncaught TypeError: Cannot read properties of undefined (reading 'position')
    at computeOverlapGroups (linkOverlap.js:44:73)
```

원인: `CUSTOM_DIAGRAM_TYPE`에서 `CustomBlock`의 이벤트 행(`CustomEventBlock`)에서
나가는 링크는 `blockOrigin`이 부모 블록이 아니라 **그 행 자체**이고, 행의
`anchors`는 L/T/R/B가 아니라 **그 행의 이벤트 이름 하나로만** 등록돼 있다(7번
섹션에서 이 구조를 직접 다룰 때 이미 확인했던 내용인데, 6번 섹션 anchor
재연결 로직을 짤 때는 이 사실을 놓치고 "모든 링크의 origin/dest는 L/R/T/B
anchor를 가진 블록"이라고 가정해버렸다). 그래서
`component.blockOrigin.anchors.get('R')`가 이런 행-origin 링크에서는
`undefined`를 반환하는데, 이걸 그대로 `link.anchorFrom`에 대입해버려서 —
그 즉시는 에러가 안 나다가, 나중에 그 링크가 다시 그려질 때(블록 드래그,
겹침 배지 재계산 등 `anchorFrom.x`/`anchorFrom.position`을 읽는 모든 곳)
크래시로 이어졌다. 실측: 실제 파일 링크 299개 중 154개가 이 케이스(행-origin)
— 처음 검증 때는 이 154개를 우연히 안 건드리는 경로로 테스트해서 못 잡아냈다.

**수정**: `autoLayout.js`의 anchor 재연결 루프에서, `blockOrigin.anchors.get(...)`/
`blockDest.anchors.get(...)` 결과가 실제로 존재하는지 먼저 확인하고, 없으면
그 링크는 건드리지 않고 원래 anchor를 그대로 둔다 — 애초에 이벤트 행의 anchor는
이미 "이 링크 전용" 고정 위치라 방향에 맞춰 재배치할 필요도 없다(원래 그 자체로
`CustomBlock`이 겹침을 막으려고 설계한 지점이므로). 겸사겸사 `linkOverlap.js`의
`computeOverlapGroups`도 `anchorFrom`/`anchorTo`가 없는 링크는 건너뛰도록
방어 코드 추가 — 이 특정 버그가 아니어도 앞으로 비슷하게 깨진 링크가 생기면
겹침 배지 계산 전체가 죽는 대신 그 링크만 빠지도록.

**재검증**: 실제 파일 기준 링크 299개 중 undefined anchor 0개(수정 전 154개),
그 중 145개는 정상적으로 R→L(또는 B→T)로 재연결, 나머지 154개(행-origin)는
의도대로 원래 anchor 그대로 유지. "왼쪽→오른쪽으로" 실행 후 블록을 실제로
움직여봐도(마우스 드래그 재현 포함) 크래시 없음, 겹침 배지 재계산도 정상 동작.

**참고**: 이 저장소는 `node_modules/`가 `.gitignore`에 없어서 이미 커밋되어
있었음(4477개 파일, 이번 작업과 무관한 기존 상태) — `@dagrejs/dagre` 설치로
`node_modules/` 안쪽 파일들도 `git status`에 같이 뜬다. 커밋 시 이것까지 그대로
올릴지, 이번 기회에 `.gitignore`를 손볼지는 사용자 확인 필요.

## 7. `CustomBlock` 이벤트 행 접기/펼치기 (이벤트 많은 블록의 세로 길이 문제)

사용자가 예전에 만든 `CUSTOM_DIAGRAM_TYPE`(사각형 블록마다 이벤트/선택지를 블록
아래 쌓이는 행으로 보여줘서, 링크가 겹쳐도 클릭 안 해도 뭔지 알 수 있게 하는
구조 — `diagram-library.js`의 `CustomBlock`/`CustomEventBlock`)을 분석해달라는
요청에서 출발. 분석 중 **이게 죽은 코드가 아니라 지금 앱의 실제 기본값으로
동작 중**이라는 걸 확인(`Diagram.defaultOptions.blockType`이 `CUSTOM_DIAGRAM_TYPE`,
`App.jsx`/`DiagramCanvas.jsx` 어디도 이걸 덮어쓰지 않음 — 실측: 실제 파일에서
사각형 블록 61개가 전부 `CustomBlock`). 실제 데이터에서 이벤트 33개짜리 블록을
발견 — 세로 길이가 약 1500px까지 늘어나는 문제를 어떻게 다듬을지 검토 후 진행.

**검토했던 안**: 접기/펼치기(요약 행), 다단 배치, 행 높이 압축, 목적지 기준 병합 —
사용자가 접기/펼치기를 선택. 링크 처리 방식도 "완전히 숨김"(옵션 a, 가장 단순한
버전)으로 우선 진행하기로 함.

**구현**: 이번엔 `diagram-library.js`를 직접 수정 — CustomBlock은 이 파일에 정의된
사용자 자신의 기능이라, 외부에서 우회하는 대신 그 자리에서 확장하는 게 맞다고
판단.

- `CUSTOM_EVENT_COLLAPSE_THRESHOLD = 8` 상수 추가 — 이벤트가 이 개수를 넘으면
  앞쪽 7개(threshold-1)만 보여주고 나머지는 "+N개 더보기" 요약 행 하나로 접음.
- `CustomEventBlock.setVisible(visible)` — 행 자체(`shapeElement`/`addActionArea`)와
  그 행에 연결된 링크(있다면 `shapeElement`/`textElement`)를 통째로 display:none
  처리. `shapePointElement`/`connectPointElement`는 원래도 hover/선택 시에만
  잠깐 보이는 요소라, 숨길 때만 강제로 지우고 다시 보여줄 땐 그 자체 로직에 맡김
  (건드리면 항상 보이는 상태로 고정되는 회귀가 생김).
- `CustomBlock._syncEventVisibility()` — 개수와 펼침 여부로 보일 행 수를 계산해서
  각 행에 `setVisible()` 호출, 요약 행(`_ensureSummaryRow()`가 지연 생성)의 위치와
  텍스트("+N개 더보기" / "접기")를 갱신. **기존 행의 인덱스 기반 위치 계산 로직은
  전혀 안 건드림** — 숨겨진 행도 원래 자리에 그대로 있고(`display:none`일 뿐)
  요약 행만 별도로 그 위에 얹는 방식이라, `movePosition`/`alignRelativeSize`/
  `_reArrange`/`contextMenuClick`/`eventDeserialize` 같은 기존 코드는 손대지
  않고 그 뒤에 `_syncEventVisibility()` 호출 한 줄씩만 추가.
- undo/redo(`CUSTOM_EVENT_ADDED`/`CUSTOM_EVENT_REMOVED`) 경로도 전부 확인해서
  `_syncEventVisibility()`를 빠짐없이 연결 — `_deleteMenu()`를 거치는 경로는
  자동으로 커버되고, `eventElementArray.push` 직후 경로(추가 redo, 삭제 undo)
  2곳만 별도로 추가.
- 요약 행은 실제 `Block`/`Link`가 아닌 순수 UI 토글이라 `'draggable'` 클래스를
  일부러 안 줌 — 줬다면 SVG 레벨 드래그 핸들러가 `data-id`로 컴포넌트를 찾으려다
  실패했을 것.
- `Block.remove()`(공용)에 요약 행 DOM 정리 한 줄 추가 — 블록 삭제 시 고아
  엘리먼트로 안 남게.
- 펼침 상태는 세션 동안만 유지(파일에 저장 안 함) — 다시 열면 항상 접힌 채로
  시작. 필요하면 나중에 userData에 저장하는 것도 가능.

**검증 (Playwright, 실제 이벤트 33개 블록 "음성인식메인")**:
- 로드 직후: 33개 중 7개만 보이고 나머지 26개는 숨김, 요약 행 "+26개 더보기"
  표시 확인. 숨겨진 행에 연결된 링크의 `shapeElement.style.display`도 `'none'`
  확인.
- 요약 행 클릭 → 33개 전부 보임 + 요약 행 텍스트가 "접기"로 바뀜 확인.
- 다시 클릭 → 정확히 7개+요약 행으로 되돌아옴 확인.
- 이벤트 8개 이하인 일반 블록 5개 샘플 확인 — 전부 요약 행 자체가 안 생기고
  모든 행이 그대로 보임(회귀 없음).
- 스크린샷으로 접힌/펼친 두 상태 모두 눈으로 확인.

**참고 — 별도로 발견한 콘솔 에러 (원인은 8번 섹션에서 정정)**: 검증 중 콘솔에
`<circle> attribute cx: Expected length, "null".` 류의 에러가 다수 뜨는 걸
발견 — 처음엔 `getOptimalCustomRoute`(Custom 모드 링크 경로 계산)의 기존 버그로
추측하고 이번 작업 범위 밖이라 넘어갔었는데, **이 추측은 틀렸다**. 실제 원인은
겹친 링크 배지 기능(`linkOverlap.js`, 지난 커밋에서 만든 것) 자체의 버그였고,
사용자가 다시 지적해줘서 8번 섹션에서 제대로 찾아 고쳤다.

## 8. 버그 수정 — 겹친 링크 배지가 항상 좌표 (0,0) 근처에 잘못 표시되던 문제

사용자가 실사용 중 콘솔에서 아래 에러를 발견하고 다시 알려줌:
```
Error: <circle> attribute cx: Expected length, "null".
    at positionBadge (linkOverlap.js:146)
Error: <circle> attribute cy: Expected length, "null".
Error: <text> attribute x: Expected length, "null".
Error: <text> attribute y: Expected length, "null".
```

지난 6번 섹션 버그 수정 (3) 작업 중 이미 한 번 이 에러를 본 적이 있었는데, 그때는
"페이지를 열기만 해도 나니까 이번 작업과 무관한 `diagram-library.js`의 기존
버그(`getOptimalCustomRoute`)"라고 잘못 결론 내렸었다. **다시 파보니 완전히
틀린 진단이었다** — 실제 원인은 겹친 링크 배지 기능(`linkOverlap.js`, 지난
커밋 `b6b46f5`에서 만든 기능) 자체에 있었다.

**진짜 원인**: `syncLinkOverlapBadges`가 배지 위치를 `link.shapePointElement`의
`cx`/`cy` 속성값을 읽어서 정하도록 만들었었는데(겹친 링크 기능 설계 당시
"`Link.adjustPoints()`가 이미 계산해둔 라벨 위치라 별도 좌표 계산 불필요"라고
가정했음), 이 가정 자체가 틀렸다. `Link.adjustPoints()`를 직접 읽어보면
`lineType === NORMAL_DIAGRAM_TYPE`일 때만 `shapePointElement`/`textElement`의
좌표를 채워주고, `lineType === CUSTOM_DIAGRAM_TYPE`(6번 섹션에서 확인했듯
이 앱이 실제로 쓰는 모드)일 때는 그 두 엘리먼트를 아예 건드리지도 않는다 —
그래서 이 앱의 모든 링크는 처음부터 끝까지 `shapePointElement`의 `cx`/`cy`가
단 한 번도 채워진 적이 없었다(`getAttribute()`가 JS `null` 반환). 그 `null`을
그대로 배지 원/텍스트의 `cx`/`cy`/`x`/`y`에 `setAttribute()`로 옮겨버리니
브라우저가 문자열 `"null"`로 취급해서 에러를 내면서 좌표를 0으로 처리 — 결과
겹친 링크 배지 10개가 전부 화면 좌표 (0,0) 근처(정확히는 그냥 0)에 겹쳐서
잘못 그려지고 있었다.

**수정**: 배지 위치를 `shapePointElement`가 아니라 **링크가 실제로 그려진
경로(`link.shapeElement`, `<path>`)에서 직접 구하도록** 변경 —
`path.getPointAtLength(path.getTotalLength() / 2)`로 경로의 실제 중간 지점을
구한다. 이 방식은 `lineType`이 Normal이든 Custom이든 상관없이 항상 유효한
`d` 속성만 있으면 되므로(둘 다 `shapeElement`의 `d`는 항상 채워짐), 어느
모드에서든 안전하다. `diagram-library.js`는 여전히 안 건드림 — `linkOverlap.js`
안에서만 고침.

**검증 (Playwright, 실제 `123.prj` 파일)**:
- 수정 전: 배지 10개 전부 `circleElement`의 `cx`/`cy`가 문자열 `"null"`.
- 수정 후: 10개 전부 실제 좌표(예: `cx: 538, cy: 348.96` — 51개 겹친 링크
  배지, 다른 것들도 각자 다른 좌표)로 정상 표시. 콘솔 에러 0건(수정 전엔 배지
  1개당 4개씩, 총 40개— 재계산이 여러 번 겹치면 더 많이 뜸).
- 스크린샷으로 "51" 배지가 실제로 그 링크(재인입 체크 근처) 위에 올라가 있는
  것을 눈으로 확인 — 수정 전에는 화면 왼쪽 위 구석에 몰려있었을 것(이번엔
  수정 후 상태만 스크린샷으로 남김).

**교훈 삼아 남겨둠**: 처음 진단할 때 "이 작업과 무관하게 페이지 로드만 해도
나는 에러니까 기존 라이브러리 버그"라고 넘겨짚었던 게 틀렸다 — 실제로는 내가
만든 코드(`linkOverlap.js`)가 페이지 로드 직후(구성 단계에서 `syncLinkOverlapBadges`
최초 호출) 바로 실행되기 때문에 "로드하자마자 난다"는 것만으로는 원인이
라이브러리인지 내 코드인지 구분이 안 됐던 것. 에러 스택 트레이스(`positionBadge`,
`linkOverlap.js:146`)를 처음부터 제대로 봤으면 바로 알 수 있었다.

**수정된 파일**
- `src/lib/linkOverlap.js` — `linkMidpoint(link)` 헬퍼 추가,
  `syncLinkOverlapBadges`가 `shapePointElement` 대신 이걸로 배지 위치 계산.

## 9. `CustomBlock`의 "+" 버튼 — 네이티브 목록 대신 `LinkEventPicker` 재사용

사용자 지적: `CustomBlock`(사각형 블록)을 클릭하면 머리 위에 뜨는 "+" 버튼이,
Normal 모드에서 링크를 드래그로 만들 때 뜨는 것과 같은 (meta 기반) 이벤트 선택
창으로 뜨면 좋겠다는 요청.

**기존 상태 확인**: "+"를 누르면 `loadContextMenu()`가 `component.initArray`
(생성자에 박혀있는 범용 배열 `['1'..'9','0','defaults','ok','error','default']`)로
순수 HTML `<ul class="fm-menu">` 목록을 그려서 보여줬다 — 그 노드 타입이 실제로
허용하는 이벤트가 뭔지(`designer.meta.json`의 `links`)와 전혀 무관한, 범용
숫자/문자 목록이었다. 반면 Normal 모드는 이미 `onLinkCreating` 콜백을 통해
`LinkEventPicker.jsx`(meta의 `links` 정의를 읽어서 실제 선택 가능한 이벤트만
보여주고, 이미 쓰인 건 "사용됨"으로 비활성화, meta에 `links`가 없으면 자유
입력 `prompt()`로 폴백)를 띄우고 있었다 — 이 컴포넌트를 CustomBlock의 "+"에도
그대로 재사용하기로 함.

**구현**: `onLinkCreating`과 완전히 같은 "요청/응답 콜백" 패턴으로
`diagram.options.onCustomEventAdding(block, e, callback)`을 새로 추가.
- `diagram-library.js`: `Diagram.defaultOptions`에 `onCustomEventAdding: null`
  추가. "+" 클릭 핸들러(`_mousedown`의 `addEvent` 분기)를 이 옵션이 있으면
  위임하고, 없으면 기존 `loadContextMenu()`로 폴백하도록 수정(하위 호환 유지).
  `CustomBlock.contextMenuClick`에서 실제로 행을 추가하는 부분을
  `addEventRow(command)`로 분리해서, 네이티브 목록 경로와 새 픽커 경로 둘 다
  같은 로직을 공유하게 함(dialog/contextMenu 정리는 각자 다른 UI라 호출자
  책임으로 남김).
- `DiagramCanvas.jsx`: `onCustomEventAdding` 핸들러를 `onLinkCreating`과 거의
  동일하게 등록 — 같은 `linkPicker` state, 같은 `<LinkEventPicker>` 렌더를
  그대로 재사용(새 컴포넌트 안 만듦). "이미 쓰인 이벤트" 판정만 다름 —
  `onLinkCreating`은 실제 나간 링크의 caption 기준, 여기는 아직 링크가 없는
  이벤트 행 목록(`block.eventElementArray.map(row => row.event)`) 기준.

**검증 (Playwright)**: `WaitCallNode`("수신 대기", meta에 `links` 4개: answered/
ringing/error/timeout) 삽입 → 선택 → "+" 클릭 → `LinkEventPicker`가 뜨고
네이티브 `.fm-menu`는 안 뜸, 옵션 4개가 정확히 표시되고 "answered"에 "필수"
배지 확인 → "answered" 선택 → 실제 이벤트 행 추가됨 확인 → "+"를 다시 눌러서
"answered"가 비활성화 + "사용됨" 배지로 표시되는지 확인. `HangupNode`("전화

**수정된 파일**

## 10. Circle/Diamond 노드도 Custom 모드에서 `CustomBlock`으로 — 링크 겹침을
    구조적으로 제거

사용자 관찰: 사각형↔사각형 링크는 자연스러운데, 사각형↔원/사각형↔다이아몬드는
경로가 조금 어색해 보인다는 지적. 원인 조사 결과 두 가지가 겹쳐 있었다 —
(1) `getOptimalCustomRoute`가 목적지 `CustomBlock`에는 어느 변인지 안 따지는
단순 분기를 타지만, 원/다이아몬드는 anchor 방향(T/B/L/R)까지 따지는 훨씬
복잡한 분기를 타서 이벤트 행의 "항상 오른쪽에서 나감"과 안 맞으면 지그재그가
생김. (2) 6번 자동 정렬의 anchor 재연결이 이벤트 행-origin 링크는 건드리지
않아서(크래시 방지 목적), 재배치 후에도 목적지 쪽 anchor 방향이 예전 값으로
남아 어긋남이 더 심해질 수 있음.

여기서 사용자가 한 단계 더 나가서 제안: 다이아몬드도 지난번 검토(9번 이전
대화)에서 얘기했던 것처럼 아예 Custom 모드에서 `CustomBlock` 형태로 바꾸되,
원래 모양의 흔적만 위쪽 모서리 처리로 남기자 — Circle은 위쪽을 둥글게, Diamond는
위쪽을 45도로 깎아 팔각형 윗부분처럼. 승인 후 바로 진행.

**왜 이게 효과가 큰가**: `IfNode`/`SwitchNode`(분기 노드)가 전부 Diamond
모양인데, 실제 데이터에서 링크 겹침이 가장 심했던 게 정확히 이 타입(SwitchNode
"재인입 체크", 51개)이었다. 이걸 `CustomBlock`으로 바꾸면 이벤트마다 전용
행+anchor가 생겨서, 배지+팝오버로 땜빵하던 걸 **구조적으로** 없앨 수 있다.
부수적으로 목적지 쪽도 이제 전부 `detailType === CUSTOM_BLOCK`이 되어
`getOptimalCustomRoute`의 단순 분기를 타게 되므로, 애초에 지적받은 "어색한
경로" 문제도 같이 해결된다.

**구현**:
- `buildCustomBlockShapeD(x, y, w, h, shapeStyle)` 헬퍼 추가 — `shapeStyle`이
  `'roundedTop'`(원래 Circle)이면 위쪽 두 모서리를 둥근 2차 베지어로,
  `'chamferedTop'`(원래 Diamond)이면 위쪽 두 모서리를 45도로 깎은 `<path>`의
  `d`를 계산. 아래쪽은 항상 각지게(이벤트 행이 맞닿아야 하므로) 둔다.
  `'rect'`(기본, 실제 사각형 노드)는 이전과 동일하게 `null`을 반환해서 그대로
  `<rect>`를 쓴다 — 실제 사각형 노드의 동작은 전혀 안 바뀜.
- `CustomBlock` 생성자에 `shapeStyle` 파라미터 추가(기본값 `'rect'`), `shapeD`가
  있으면 `shapeElement`를 `<rect>` 대신 `<path>`로 생성. `<path>`는 `height`
  속성이 없어서 `this.accumulatedHeight` 초기화도 DOM 속성을 안 읽고
  `this.h`를 직접 쓰도록 수정.
- `movePosition`/`alignRelativeSize`: `shapeElement.tagName === 'path'`일 때는
  `x`/`y`/`width`/`height` 속성 대신 `buildCustomBlockShapeD()`로 `d`를 다시
  계산해서 갱신 — `<path>`엔 그런 속성이 없기 때문. `'rect'` 스타일(실제
  사각형 노드)은 기존 로직 그대로 유지.
- `Block.createInstance`: `CIRCLE_BLOCK_SHAPE`/`DIAMOND_BLOCK_SHAPE` 분기에서
  `diagram.options.blockType === CUSTOM_DIAGRAM_TYPE`이면 각각
  `'roundedTop'`/`'chamferedTop'`로 `CustomBlock`을 만들고, 아니면(Normal 모드,
  현재는 도달 안 함) 기존 `CircleBlock2`/`DiamondBlock2` 그대로 — 하위 호환
  유지.
- 직렬화/역직렬화는 손 안 댐 — `Block.deserialize()`가 `<choice>`를 이미 노드
  타입과 무관하게 평평하게 읽어서 `event` 배열을 채우고 있었고(설계 당시부터
  확인된 사실), `Link.deserialize`도 `block.eventElementArray.length > 0`
  여부만으로 분기해서 자동으로 잘 맞물렸다.

**검증 (Playwright)**:
- 새로 삽입한 `IfNode`/`CallPageNode`가 둘 다 `CustomBlock` 인스턴스로, 각각
  `shapeStyle: 'chamferedTop'`/`'roundedTop'`, `shapeElement.tagName: 'path'`로
  확인. 스크린샷으로 위쪽 모서리가 실제로 다르게(둥글게/45도로 깎임) 그려지는
  것 확인.
- 실제 `123.prj`(140블록, 303링크) 재로드 — 전부 `CustomBlock`, 링크 303개
  그대로(유실 없음), **겹침 그룹 10개 → 0개**(가장 심했던 51개 포함). 가장 큰
  분기 노드(id `00000703`, "재인입 체크")가 실제로 이벤트 54개짜리 `CustomBlock`
  으로 변환되어, 접기 임계값(7번 섹션)에 따라 7개+"+47개 더보기" 요약 행으로
  깔끔하게 표시되는 것 스크린샷으로 확인.
- 드래그(위치 이동) → `d` 재계산 정상. `alignRelativeSize()`로 리사이즈 →
  `w`/`h`/`d` 전부 정상 갱신. `IfNode`에 "+" 눌러 `LinkEventPicker` → 실제
  meta 이벤트(`true`/`false`/`error`) 표시, 선택 시 행 추가 정상 — 9번에서
  만든 기능이 다이아몬드에도 그대로 적용됨을 확인.
- 콘솔 에러 없음.

**버그 발견 및 수정 — 사용자가 실사용 중 발견: 드래그/행 삭제 후 이벤트 행이
블록에서 멀리 떨어짐**

위 검증까지는 "삽입 직후" 상태만 확인했는데, 사용자가 실제 파일(다이아몬드가
많이 바뀐 파일)로 써보다가 블록을 옮기거나 행을 하나 지운 뒤에 **이벤트 행들이
부모 블록과 완전히 동떨어진 위치에 붙는** 버그를 스크린샷으로 발견해서 알려줌.

원인: `CustomEventBlock.relocation()`(드래그 시 각 행 위치 갱신)과 `_reArrange()`
(행 삭제 후 나머지 행 재정렬)가 부모 블록의 높이/y좌표를
`this.block.shapeElement.getAttribute('height'/'y')`로, 즉 **DOM 속성을 직접
읽는 방식**으로 구해오고 있었다. 실제 사각형 노드(`<rect>`)일 때는 이 속성들이
항상 있어서 문제가 없었는데, 이번에 Circle/Diamond를 `<path>`로 바꾸면서
(10번 위쪽 내용) `<path>`엔 애초에 `height`/`y` "속성" 자체가 없다(도형 전체가
`d` 하나에 들어있음) — 그래서 `getAttribute()`가 `null`을 반환하고 `parseFloat(null)`이
`NaN`이 되어, 행들이 `NaN` 좌표 근처의 알 수 없는 위치로 튀었다.

**수정**: 두 메서드 다 DOM 속성 대신 **항상 정확히 갱신되는 JS 상태**
(`this.block.h`, `this.block.y`)를 직접 읽도록 변경 — 이 값들은 `<rect>`든
`<path>`든 상관없이 블록 객체 자신이 항상 들고 있는 진짜 높이/y좌표라 더
안전하다(사각형 노드에도 동일하게 적용해도 결과가 똑같음 — 회귀 없음).

**재검증**: 이벤트 2개짜리 `IfNode`를 드래그 → 행 2개 다 블록 바로 아래
정확한 좌표로 따라감(스크린샷 확인). 이벤트 3개 중 첫 번째 행을 삭제 → 남은
2개가 위로 정확히 한 칸씩 당겨짐(`NaN` 없음). 실제 `123.prj` 파일에서 이벤트가
있는 블록 15개(그 중 54개짜리 포함)를 전부 드래그해본 뒤 모든 행(303개)의
좌표를 검사 — `NaN` 0개. 콘솔 에러 없음.

**수정된 파일**
- `src/lib/diagram-library.js` — `buildCustomBlockShapeD()` 추가, `CustomBlock`
  생성자/`movePosition`/`alignRelativeSize`에 `shapeStyle`/`<path>` 분기 추가,
  `Block.createInstance`의 Circle/Diamond 분기 수정, `CustomEventBlock.relocation()`
  /`_reArrange()`의 부모 높이/y 계산을 DOM 속성 대신 `this.block.h`/`this.block.y`로
  수정(위 버그 수정).
