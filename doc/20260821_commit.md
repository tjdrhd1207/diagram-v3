# 변경사항 정리 (프로젝트 파일 관리 + 레거시 XML 임포터 + 리본 UI 개선)

커밋 전 정리용 문서. 아래 여섯 덩어리로 진행됐습니다.

1. PropertyPanel 필드별 인라인 설명
2. 프로젝트 파일 관리 (새 프로젝트 / 열기 / 저장 / .prj 프로젝트 열기)
3. 레거시 ScenarioDesigner .xml 페이지 임포터 + `designer.meta.json` 전환
4. 리본 "삽입" 탭 — 카테고리 플라이아웃으로 재설계
5. 겹친 링크 — 개수 배지 + 호버 선택 팝오버
6. 스크립트 에디터 — "보이는 ARS"(WV_Param) 미리보기 탭

## 1. PropertyPanel 필드별 인라인 설명

기존엔 필드 설명이 패널 하단 한 곳에 모여 있어서, 보려면 스크롤해야 했음. 필드를
클릭하면 그 필드 바로 아래에 설명이 뜨도록 변경(3안 중 사용자가 선택한 "B. 필드
바로 아래 인라인" 방식).

- `FieldDescriptionContext`가 들고 있던 값을 "설명 문자열"에서 `{ activeFieldKey,
  setActiveFieldKey }`로 변경. 각 `Field` 호출부가 자기 `fieldKey`를 갖고 있다가,
  포커스 시 그 key를 컨텍스트에 올리고, 자기 key가 활성 key와 같을 때만 스스로 설명을
  그린다.
- 노드 레벨 설명(`nodeDescription`, 패널 맨 아래)은 필드 포커스와 완전히 분리 —
  어떤 필드에 포커스가 있든 없든 항상 표시.

**수정된 파일**
- `src/components/PropertyPanel.jsx` — `Field`가 `fieldKey` prop을 받아 컨텍스트의
  `activeFieldKey`와 비교, 자기 설명을 `children` 아래에 인라인으로 렌더링. 모든
  `Field`/`ScriptEditorField` 호출부에 `fieldKey` 배선.
- `public/css/property-panel.css` — `.property-field-description` /
  `.property-field-description-icon` 추가 (기존 하단 전용 `.property-panel-description`과
  시각적으로 비슷하지만 훨씬 작고 필드 바로 아래에만 나타남).

## 2. 프로젝트 파일 관리 (새 프로젝트 / 열기 / 저장 / .prj 프로젝트 열기)

as-is 도구처럼 파일을 불러오고 저장하는 기능이 전혀 없던 상태에서, 리본 "파일" 탭에
전체 파일 관리 기능을 새로 만듦.

**단일 파일 열기/저장**
- "새 프로젝트": 확인창 후 캔버스를 완전히 새로 시작. `DiagramCanvas`가 마운트 시점에
  딱 한 번 `Diagram` 인스턴스를 만드는 구조라, `canvasKey`를 올려서 컴포넌트 자체를
  리마운트시키는 방식으로 구현 (새 `useId` → 새 svgId → 새 `Diagram`).
- "열기": `.xml` 파일 하나를 골라 `FileReader`로 읽고 `initialXml`에 담아 캔버스를
  리마운트. `DiagramCanvas`는 `initialXml`이 있으면 `new Diagram()` 대신
  `Diagram.deserialize()`로 시작하도록 분기.
- "저장": `Diagram.serialize()` 결과를 `scenario.xml`로 다운로드.
- `DiagramCanvas`에 `findMissingMetaNames()` 사전 검사 추가 — `Block.deserialize()`가
  `meta.nodes[metaName]`을 가드 없이 읽어서 없는 타입이면 그 자리에서 크래시하는데,
  실제로 호출하기 전에 미리 훑어서 어떤 타입이 빠졌는지 알림으로 알려주고 빈 캔버스로
  안전하게 폴백하도록 함.
- 모든 `FileReader` 사용처에 `onerror` 핸들러 추가 — 이게 없으면 읽기 실패가 완전히
  조용해서(`onload`가 그냥 안 불림) "클릭했는데 아무 일도 안 일어남"으로만 보였음.

**`.prj` 프로젝트 열기 (폴더 선택)**
- `.prj`는 시나리오가 아니라 **프로젝트 인덱스**임을 실제 샘플로 확인 — 프로젝트
  전역 변수/공용 스크립트/빌드 설정 + `<ItemGroup><Page Include="파일명.xml"
  Tag="메뉴이름">` 나열만 갖고 있고, 실제 시나리오는 같은 폴더의 개별 `.xml`
  파일들에 있음.
- `webkitdirectory` 폴더 선택으로 `.prj`와 그 옆의 `.xml`들을 한 번에 읽어들여서,
  `ProjectPagesPanel`(검색 가능한 평평한 페이지 목록, 캔버스 왼쪽)에 표시. `IsStart`
  페이지를 자동으로 캔버스에 로드.
- 폴더에 실제로 없는 페이지는 "파일 없음" 배지 표시. 처음엔 `disabled` 버튼으로
  막았었는데, disabled면 `onClick` 자체가 안 떠서 "클릭해도 반응 없음"으로 보이는
  문제가 있어 — 클릭은 항상 되게 하고 없으면 alert로 명확히 알려주는 방식으로 수정.

**추가된 파일**
- `src/lib/prjFile.js` — `.prj` XML 파서 (`parsePrjXml`, `findPrjFile`,
  `buildFileIndex`).
- `src/components/ProjectPagesPanel.jsx` — 페이지 목록 사이드 패널 (검색 + 평평한
  목록, 파일명 접두사로 계층이 느껴지지만 `.prj`에 명시적 부모-자식 필드가 없어서
  트리로 재구성하지 않음).
- `public/css/project-pages-panel.css`

**수정된 파일**
- `src/App.jsx` — `canvasKey`/`initialXml`/`project`/`activePageInclude` 상태,
  파일/폴더 입력 두 개(숨김), 관련 핸들러 전부.
- `src/components/DiagramCanvas.jsx` — `initialXml` prop, `Diagram.deserialize()`
  분기, `findMissingMetaNames()`, `onLoadError` prop, `serialize()` 메서드
  (`useImperativeHandle`).
- `src/components/RibbonMenu.jsx` — "파일" 탭에 새 프로젝트/열기/프로젝트 열기/저장
  버튼 추가.

**특이점**
- **진짜 버그 하나 발견**: `e.target.files`는 input에 물려있는 "라이브" `FileList`라,
  읽은 직후 `e.target.value = ''`로 리셋하면 이미 들고 있던 참조까지 같이 비어버림
  (같은 객체를 나중에 다시 읽어도 length가 0). 폴더 선택 핸들러에서 이걸로 파일이
  통째로 사라지는 문제가 있었음 — `[...e.target.files]`로 즉시 배열 복사해서 해결.
  단일 파일 열기 쪽은 `File` 객체를 바로 인덱싱해서 뽑아뒀기 때문에 원래 문제 없었음
  (`File` 자체는 라이브가 아니라 `FileList` 컨테이너만 라이브).
- `diagram-library.js`는 이번에도 전혀 건드리지 않음.

## 3. 레거시 ScenarioDesigner .xml 페이지 임포터 + `designer.meta.json` 전환

`.prj`가 가리키는 실제 페이지 파일(`123.xml`)을 열어보니 화면에 아무것도 안 나타나서
조사한 결과, 실제 파일이 `Diagram.serialize()`/`deserialize()`가 다루는
`<scenario><block>` 포맷이 아니라 **디자이너 자체 편집 포맷**
(`<Diagram><Nodes><Node NodeType="...">`, .NET 직렬화기가 그대로 찍어낸 형태)임을
확인. 실제 샘플(`123.prj`, `123.dxml`, `123.xml`)을 직접 대조해서 변환 규칙을 확정.

또한 작업 도중 기존 `sample-meta.json`(13종 노드)이 `designer.meta.json`(66종 노드,
사용자가 새로 제공)으로 교체되면서 `App.jsx`의 import가 깨져 있던 것도 같이 고침.

**매핑 규칙 (실제 파일 대조로 확정)**
- `NodeType` 속성이 그대로 우리의 meta-name (역매칭 불필요).
- `<Bounds>x, y, w, h</Bounds>`가 그대로 `<svg><bounds>x,y,w,h</bounds></svg>` —
  **좌표가 원본에 있어서 자동배치가 필요 없음** (`.dxml`은 빌드 산출물이라 좌표가
  아예 없어서 자동배치가 필요했을 것 — 그래서 `.dxml`이 아니라 `.xml` 기준으로
  가기로 결정).
- 링크의 `Origin`/`Destination`은 `<Node>`의 파일 내부 임시 `Id`(0,1,2,...)를
  참조하므로, 전체 `<Nodes>`를 먼저 스캔해 `내부Id → Sequence`(우리 block id) 맵을
  만들고 치환.
- `<Links>`가 노드 타입과 무관하게 실제 존재하는 모든 분기를 그대로 나열함을
  확인(`SwitchNode` 같은 "동적 분기" 타입도 예외 아님 — 실제 `.dxml`의 `<switch>`
  블록이 다른 노드와 동일한 평범한 `<choice>` 구조였음) — 그래서 노드 타입별 특수
  처리 없이 모든 타입을 동일한 알고리즘으로 처리 가능.
- 프로퍼티는 `designer.meta.json`의 `sourceName`(디자이너 필드명) → `buildName`
  (우리 시스템이 쓰는 이름) 매핑을 그대로 기계적으로 적용. `buildDataType`이 있으면:
  - `'CData'` → 속성이 아니라 자식 엘리먼트 + 텍스트로 (예: ScriptNode의 Script →
    `<javascript><source>...</source></javascript>`).
  - `'XmlChild'` → 원본 서브트리를 그대로 복제해서 태그 이름만 buildName으로 교체.
  - `buildName`이 빈 문자열이면 저장 대상이 아니므로 건너뜀 (예: SwitchNode의
    `SwitchCase` — 실제 분기는 `<Links>`에서 이미 나옴).
- `buildScript` 필드(빌드 산출물 생성 전용 변환식)는 이 임포터(편집용 불러오기)에는
  적용하지 않음 — 원본 값을 그대로 보존.
- **후속 버그 수정**: 처음엔 `<Link>`의 `<OriginAnchor>`/`<DestinationAnchor>`(링크가
  블록의 어느 변에 붙는지, 0=왼쪽/1=위/2=오른쪽/3=아래)를 안 옮겨서, 실제로 불러온
  파일에서 **모든 링크가 예외 없이 오른쪽 anchor에만 붙는** 문제가 있었음
  (`diagram-library.js`의 `Link.deserialize()`가 `svg-origin-anchor`/`svg-dest-anchor`
  속성이 없으면 항상 `convertAnchorPosition.default`(오른쪽)로 폴백하기 때문). 다행히
  디자이너 XML의 0~3 숫자 코드가 `convertAnchorPosition`의 키와 정확히 같은 체계라,
  변환 없이 그대로 `choice`의 `svg-origin-anchor`/`svg-dest-anchor` 속성에 옮기는
  것으로 해결. 실제 파일로 재검증: 앵커 조합이 `R->R`(303개 전부)에서 `R->L`/`B->T`/
  `L->R` 등 실제 배치에 맞게 다양하게 나오는 것 확인.

**추가된 파일**
- `src/lib/designerXml.js` — `looksLikeDesignerXml()`(루트 태그로 빠르게 판별),
  `convertDesignerXmlToScenarioXml()`(위 규칙을 그대로 구현).

**수정된 파일**
- `src/App.jsx` — meta import를 `sample-meta.json` → `designer.meta.json`으로 교체.
  `handleFileSelected`/`loadPageIntoCanvas`에서 읽은 텍스트를
  `resolveScenarioXml()`(디자이너 포맷이면 변환, 아니면 그대로 통과)에 거쳐서
  `initialXml`에 반영. 변환 중 meta에 없는 노드 타입이 있으면 알림.
- `src/components/PropertyPanel.jsx` — **진짜 버그 수정**: 모든 프로퍼티를 항상
  `userData.attr(buildName)`로만 읽고 썼는데, `CData`/`XmlChild` 프로퍼티는 애초에
  속성이 아니라서 늘 `null`만 반환하고 쓰기도 조용히 무시되고 있었음(스크립트 계열
  프로퍼티가 항상 빈 에디터로 보이는 원인). `readPropertyValue`/`writePropertyValue`
  헬퍼로 `buildDataType`에 따라 분기하도록 수정.
- `scripts/gen-util-dts.cjs` — `designer.meta.json`에 이미 구조화된 `utilFunctions`
  (label/insertText/documentation)가 있어서, 기존의 `ScriptNode.description` 텍스트
  정규식 파싱 방식을 걷어내고 그 배열을 그대로 `.d.ts`로 변환하도록 단순화.
  `src/lib/scriptUtilTypes.generated.js`도 재생성(51개 함수).
- `src/components/DiagramCanvas.jsx` / `src/lib/blockGrouping.js` — `sample-meta.json`
  언급 주석을 `designer.meta.json`으로 갱신 (로직 변경 없음).

**검증 (실제 `123.prj` + `123.xml`, 1.5MB, 합성 데이터 아님)**
- 140개 블록 전부 로드, 타입별 개수까지 정확히 일치 (ScriptNode 34, GotoPageNode 35,
  SwitchNode 5 등 16종).
- `IfNode`의 `condition` 값과 true/false 링크 정상 연결.
- `ScriptNode`의 실제 스크립트(1906자)가 에디터에 화면으로도 정확히 표시됨 (CData
  버그 수정의 실제 회귀 테스트).
- `SwitchNode`의 동적 분기 7개 전부 정상 연결 — "동적 분기도 특수 처리 불필요"
  가설 확정.
- `designer.meta.json`이 실제 파일의 노드 타입을 전부 커버(스킵된 타입 없음),
  콘솔 에러 없음.

**특이점**
- `diagram-library.js`는 이번에도 전혀 건드리지 않음 — 변환은 전부 `designerXml.js`
  안에서 끝내고, 결과물만 기존 `Diagram.deserialize()`에 그대로 넘김.
- `CData` 데이터를 진짜 `<![CDATA[...]]>` 섹션으로 쓸 필요는 없었음 — 일반 텍스트
  노드로 저장해도 직렬화 시 특수문자가 엔티티 이스케이프되어 왕복이 정확히 보존됨
  (`NodeWrapper.toString()`이 처리).
- 범위 밖으로 명시: `MemoNode` 변환(블록/링크만 다룸), `GotoPageNode`/`CallPageNode`가
  다른 페이지를 가리킬 때 자동 이동, `RawXML` 타입 프로퍼티 전용 편집 UI.

## 4. 리본 "삽입" 탭 — 카테고리 플라이아웃으로 재설계

`designer.meta.json` 전환으로 노드가 13종 → 66종으로 늘면서, 삽입 탭을 열면 화면
절반 가까이 차지하는 문제가 생김. 카테고리 버튼 한 줄 + 클릭 시 플라이아웃 드롭다운
방식으로 재설계 (여러 안 중 사용자가 "카테고리 드롭다운" 선택).

- 리본은 이제 다른 탭들과 같은 높이 — 색상별 카테고리 버튼 4개(시나리오/컨트롤/
  음성/서비스, 항목 수 배지 포함)만 한 줄에 보임.
- 카테고리 클릭 시 그 아래 플라이아웃: 검색창(타이핑으로 즉시 필터링) + 노드 그리드.
  바깥 클릭이나 노드 선택 시 자동으로 닫힘.
- **그리드 칸 크기 문제**: 처음엔 고정 68px 칸에 라벨을 2줄+말줄임(`...`)으로
  넣었는데, "CTI 호전환"/"CTI 호전환 완료"/"CTI 호전환 재접속"처럼 접두어가 같은
  라벨들이 전부 "CTI 호전환..."로 뭉개져 구분이 안 된다는 피드백. 말줄임을 없애고,
  캔버스 2D 컨텍스트로 그 카테고리에서 가장 긴 라벨의 실제 렌더링 폭을 측정해서
  모든 칸을 그 폭에 맞추도록 변경 — 라벨이 전부 한 줄로 잘리지 않고 보임. 플라이아웃
  전체 폭도 칸 폭×열 개수(최대 4열)로 같이 계산해서, 짧은 라벨 카테고리는 여전히
  촘촘하게, 긴 라벨이 있는 카테고리는 자동으로 넓어짐.

**수정된 파일**
- `src/components/RibbonMenu.jsx` — 기존 `groupNodesByCategory` 순회 렌더링을
  `InsertCategoryRow`/`InsertCategoryFlyout`로 교체. `measureWidestLabelWidth()`가
  칸 폭을, 그 결과로 플라이아웃 폭을 계산.
- `public/css/ribbon-menu.css` — `.ribbon-insert-*` 클래스 전부 신규. 칸 폭은

**특이점**

## 5. 겹친 링크 — 개수 배지 + 호버 선택 팝오버

실제 `.xml`을 불러왔을 때, 같은 두 블록 사이에 origin/dest anchor가 완전히 같은
`<choice>`가 여러 개 있으면 좌표가 100% 겹쳐서 라벨 텍스트가 서로 뭉개져 보이는
문제(`hlbsangnswer`처럼 보이던 것)를 발견 — 원인과 해결 방향을 실제 데이터로
검토한 뒤 진행.

**원인 분석**: `Link.getCurveRoute()`는 두 anchor 좌표(+`moveX`/`moveY`, 기본 0)만
으로 경로를 계산하므로, `(origin block, origin anchor, dest block, dest anchor)`가
같은 링크는 좌표가 완전히 동일하게 계산됨. 처음엔 "원본 디자이너 XML의 실제 곡선
데이터(`<Points>`)를 복원하면 되지 않을까" 검토했으나, 실제 `123.xml`을 분석해보니
**같은 origin/dest 쌍을 공유하는 28개 링크 그룹 중 25개(89%)가 그룹 내 모든 링크의
`<Points>` 좌표까지 완전히 동일** — as-is 데스크톱 도구 자체도 이미 겹친 채로
저장돼 있었음. 즉 원본 좌표를 복원해도 대부분 해결 안 됨. 그래서 기하학적으로
벌리는 대신, 겹친 묶음을 배지로 표시하고 호버로 골라 선택하는 방식으로 결정
(몇 개가 겹치든 UI 비용이 동일해서 안정적).

**추가된 파일**
- `src/lib/linkOverlap.js` — `(blockOrigin.id, anchorFrom.position, blockDest.id,
  anchorTo.position)` 키로 링크를 그룹화(`computeOverlapGroups`), 2개 이상 겹친
  그룹마다 원본 라벨(`link.textElement`)을 숨기고 개수 배지(SVG `<g>`)를 그 자리에
  그림(`syncLinkOverlapBadges`). 배지 호버 시 그룹 내 각 링크의 `caption`을 나열한
  팝오버(순수 DOM `<div>`)가 뜨고, 클릭하면 그 `Link.select()` 호출. 순수
  vanilla DOM만 사용(React 개입 없음, `blockGrouping.js`와 같은 스타일) —
  `diagram.linkOverlapBadges`는 런타임 전용 파생 데이터라 직렬화 대상 아님.
- `public/css/link-overlap.css` — 배지(파란 원 + 흰 숫자)와 팝오버 스타일.

**수정된 파일**
- `src/components/DiagramCanvas.jsx` — `syncLinkOverlapBadges()`를
  `reconcileGroupBounds()`가 이미 걸려있는 지점들에 그대로 얹음: 최초 로드 직후,
  `diagram.svg`의 `mouseup`(블록 드래그로 anchor 위치가 바뀌거나 드래그로 새 링크를
  연결한 직후), 그리고 `undo`/`redo`/`paste`/`remove`(마우스업 없이도 링크가
  추가/삭제될 수 있는 경로) 끝에.

**검증 (실제 `123.xml`)**
- 배지 27개 생성, 가장 큰 그룹(51개 겹친 링크) 정상 표시.
- 호버 시 팝오버에 51개 항목(`03`, `62504`, `2860`...) 전부 나열.
- 항목 클릭 시 해당 `Link`가 `selected: true`로 바뀌고 팝오버 닫힘.
- 겹치지 않는 일반 링크는 `textElement.style.display`가 그대로 `''`(보임) —
  건드리지 않았음 확인.

**특이점**
- `diagram-library.js`는 이번에도 전혀 건드리지 않음 — `Link`가 이미 공개하는
  필드(`blockOrigin`, `blockDest`, `anchorFrom.position`, `anchorTo.position`,
  `textElement`, `shapePointElement`, `caption`, `select()`)만으로 구현.
- 배지 위치는 `link.shapePointElement`의 `cx`/`cy` 속성을 그대로 읽어서 씀 —
  `Link.adjustPoints()`가 이미 계산해둔 라벨 위치라 별도 좌표 계산이 필요 없었음.

## 6. 스크립트 에디터 — "보이는 ARS"(WV_Param) 미리보기 탭

as-is의 "보이는 ARS" 화면은 ScriptNode가 `app.WV_Param`에 `TIT$/TXT$/MNT$/BTN1$/...`
같은 `$`/`;` 구분 토큰 문자열을 조립해서 만든다(사용자가 실제 운영 스크립트가 담긴
레퍼런스 시뮬레이터 HTML을 공유해줘서 실제 형식 확인). 스크립트 에디터에서 지금
작성 중인 스크립트를 실행해보면 실제로 어떤 화면이 나오는지 바로 볼 수 있는 탭을
추가.

**범위를 좁힌 과정(사용자와 논의)**: 처음엔 "스크립트 체인 실행(여러 블록에 걸친
상태 공유) + 화면 템플릿별 정확한 레이아웃 재현"까지 고려했으나, (1) 체인 실행은
외부 입력값을 사람이 매번 채워야 해서 복잡도 대비 효용이 낮고, (2) 화면 템플릿
코드(`S$`)가 사이트마다 다를 수 있어 정확한 레이아웃 재현 자체가 무리라는 결론 —
**지금 편집 중인 스크립트 하나만 실행해서, 토큰을 인식 가능한 요소로 순서대로
쌓아 보여주는 "대략적인 목업"** 으로 범위를 확정했다.

**추가된 파일**
- `src/lib/wvParamPreview.js` — `runScriptForWvParam()`(스크립트를
  `new Function('app','util', ...)`로 그대로 실행해 `app.WV_Param`을 뽑음, `util.*`는
  Proxy로 무엇을 호출하든 안 죽고 로그만 남기도록 mock), `buildMockScreen()`(토큰을
  `TIT/TXT/IMG/STEP/STR/MNT/MSG`는 화면 요소로, `BTN1/BTNE2/NEX/PRE`는 버튼으로,
  `S/BTNF/BOT/MUTE/BTH`나 그 외 모르는 토큰은 화면 밖 참고 정보로 분류).
- `src/components/WvParamPreview.jsx` — 폰 목업 렌더링(이미지는 자리표시자, 텍스트는
  원본 HTML 그대로 — 실제 프로토콜이 `<font>` 같은 태그를 담아 보내므로).
- `public/css/wv-param-preview.css` — 축소판 폰 목업 스타일.

**수정된 파일**
- `src/components/ScriptEditorModal.jsx` — "미리보기" 토글 버튼 추가(기존 "도움말"과
  같은 슬롯을 나눠 씀 — 동시에 열면 900px 모달이 좁아짐). 타이핑 중간에 자동
  재실행하면 문법이 깨진 상태의 에러만 계속 보이게 되므로, 탭을 처음 열 때 한 번과
  "다시 실행" 버튼을 눌렀을 때만 실행.

**검증**: 실제 논의에서 나온 두 예시로 확인 — (1) `S$/IMG$/TXT$(HTML 포함)/BTNE2$/
BTNF$/BOT$`로만 구성된 단순 스크립트(이미지·색상 텍스트 2줄·버튼 1개가 정확히
렌더링됨), (2) `TIT/TXT/STEP/STR/MNT`(질문 2개)/`MSG`/`NEX`로 구성된 복합 스크립트
(모든 요소 종류가 인식되고, 의도적으로 넣은 미지원 토큰 `NOT$`도 에러 없이 참고
정보 목록으로 빠짐 확인). 에디터에서 스크립트를 수정하고 "다시 실행"을 누르면
결과가 갱신되는 것도 확인.

**특이점**
- `new Function`으로 스크립트를 그대로 실행하는 것에 대한 별도 샌드박싱은 하지
  않음 — 사용자가 직접 작성/편집 중인 자기 스크립트를 실행하는 것뿐이고, 이미
  Monaco IntelliSense가 같은 신뢰 경계에서 이 코드를 다루고 있어 새로운 신뢰 경계를
  넘는 게 아님.
- 화면 템플릿(`S$`)별 실제 레이아웃 차이는 반영하지 않음(의도된 범위 밖) — 어떤
  템플릿이든 인식된 토큰을 같은 스택형 레이아웃으로 그린다.

**추가로: 스크립트 모달 크기 조절 (네 모서리 전부)**

모달이 항상 고정 크기(`min(900px, 90vw) × min(640px, 85vh)`)였는데, 미리보기 탭까지
생기면서 좁게 느껴질 수 있어 네 모서리 전부에 드래그로 크기를 조절하는 커스텀
핸들을 추가(처음엔 오른쪽 아래 하나만 넣었다가 "4방향 다 보였으면" 피드백으로
확장). 브라우저 기본 `resize: both` 대신 우리 디자인 톤(무채색 점 3개, 호버 시
강조색)에 맞춘 SVG 핸들을 직접 그림. `Editor`에 이미 있던 `automaticLayout: true`
덕분에 Monaco가 크기 변화에 알아서 다시 레이아웃되는 것도 확인.

- `src/components/ScriptEditorModal.jsx` — `boxSize` state + `handleResizeStart(signX,
  signY)`(모서리별 부호만 다르게 넘기는 팩토리 함수 — 모달이 backdrop에 항상
  가운데정렬돼 있어서 "중심에서 멀어지는 방향으로 끌면 커진다"로 네 모서리 전부
  통일). document 레벨 mousemove/mouseup로 드래그 추적, 최소 520×360px / 최대
  뷰포트의 96%×92%로 클램프. 재사용되는 `ResizeHandle` 서브컴포넌트로 4개 렌더.
- `public/css/script-editor-modal.css` — `.script-editor-box`에 `position: relative`
  추가, `.script-editor-resize-handle-{tl,tr,bl,br}` 모서리별 위치/커서, 글리프
  하나를 `scaleX/scaleY(-1)`로 뒤집어 재사용.

**버그 두 개 연달아 발견 및 수정**:

1. 위쪽/아래쪽 핸들(tl/tr, bl/br)이 헤더·푸터 영역과 같은 자리를 차지하다 보니,
   `position: absolute`인 핸들이 z-index 없이도 non-positioned 헤더/푸터보다 항상
   위에서 그려져서 우측 상단 핸들이 "×" 닫기 버튼의, 우측 하단 핸들이 "저장"
   버튼의 모서리 몇 픽셀을 가리고 클릭을 가로챌 뻔했다(Playwright로 실제 겹침
   좌표까지 확인).
2. **1번을 고치다가 새 버그를 만듦**: 처음엔 헤더/푸터 컨테이너 전체에
   `position: relative; z-index: 1`을 줬는데, 헤더/푸터가 핸들(14px)보다 훨씬
   두껍고(약 40px) 폭 전체를 차지하다 보니 겹치는 건 모서리 몇 픽셀뿐인데 핸들
   전체 영역이 통째로 헤더/푸터 밑에 깔려버려서 **네 모서리 핸들이 전부 죽는**
   회귀가 생겼다(사용자가 "구석을 눌러도 반응 없음"으로 바로 발견). 컨테이너
   전체가 아니라 실제로 겹칠 수 있는 버튼 두 개(`.script-editor-close`,
   `.script-editor-save`) 자체에만 `position: relative; z-index: 1`을 주는
   것으로 수정 — 이제 핸들은 버튼과 겹치는 딱 그 몇 픽셀에서만 뒤로 밀리고,
   나머지 영역에서는 정상적으로 드래그된다. Playwright로 네 모서리 전부 실제
   드래그 시 크기가 바뀌는지, 닫기 버튼의 가장 구석 픽셀을 클릭해도 정상적으로
   버튼이 클릭되는지 둘 다 재확인.

**추가로: 조절한 크기를 localStorage에 저장 — 다음에 열 때도 유지**

드래그로 조절한 크기가 모달을 닫으면(컴포넌트가 언마운트되면서) 사라지던 것을,
`localStorage`(`scriptEditorModal.size` 키)에 저장해서 다음에 어떤 ScriptNode를
열든 마지막으로 조절한 크기로 시작하도록 함 — 블록별이 아니라 모달 전역 설정.

- `loadSavedBoxSize()` — `useState`의 lazy initializer로 마운트 시 한 번만 읽음.
  저장 당시보다 지금 화면이 작을 수 있으므로(다른 모니터 등) `clampBoxSize()`로
  **현재 뷰포트 기준으로 다시 클램프**해서 반환 — 그대로 믿고 쓰면 화면 밖으로
  나갈 수 있음.
- `saveBoxSize()` — 드래그가 끝나는 시점(mouseup)에 저장. 드래그 도중 매
  mousemove마다 쓰지 않도록 클로저 안에 `latestSize`를 들고 있다가 mouseup에서
  한 번만 씀(React state는 그 클로저 안에서 최신값을 보장 안 해서 별도로 들고
  있어야 했음).
- `localStorage` 접근은 프라이빗 브라우징 등에서 던질 수 있어 항상 try/catch로
  감쌈 — 실패해도 크기 조절 자체는 계속 동작(그냥 이번 세션에서만 유지).

**검증**: 크기 조절 → `localStorage`에 정확한 값 저장 → 모달 닫고 새 블록으로
다시 열었을 때 저장된 크기 그대로 복원 확인. 일부러 2000×1500을 저장해두고
뷰포트를 800×600으로 줄인 뒤 열어보니 768×552(뷰포트의 96%×92%)로 정확히
재클램프되는 것도 확인.
